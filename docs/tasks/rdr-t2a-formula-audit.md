## 要做出什么

1. **截图 → fixture 无漏**：逐张对照 `docs/research/assets/red-dragon-formulas-*.png` 重新核一遍转录，**包括组注释里的公式**。漏转的补成新行，错转的改正；每处改动在该行留可追溯的批注（原值、依据）。读不清的照旧标 `uncertain`，并在报告里列出来让用户看图定。
2. **每一行都有引擎给出的结论，没有「跳过」**。结论只有三种，测试里逐行断言：
   - 原样重放通过；
   - 在**写明的前提**下重放通过（例如「上回合已打过幸运彗星」—— 这是真实存在的局面，不是错；前提要能被引擎状态表达，而不是在测试里改数字凑）；
   - 原表有误：给出引擎算出的正确值，且改正后的整行重放通过。
   能不能把某一行归为「原表有误」由引擎的重放结果说了算，不由批注说了算。
3. **可反推**：每一行从该行的起始局面（手牌 + 水晶，**不给序列**）跑搜索，`maxDamage ≥ 表中伤害`，返回的线都过重放校验。有前提的行带着前提搜。
4. **齐件 / 缺件分组**：给每一行定一个由引擎可判定的分类 —— 起手局面里随从组件是否齐全（组件清单你从卡表和公式表自己归纳，写成常量，报告里说明理由），而不是照抄组名。两类分开出结果：每类的行数、重放 / 搜索通过数、伤害与难度分布。缺件行还要验证：把缺的那张补进手牌后，搜索能走到齐件线的伤害（或说明为什么不能）。
5. REFORK 遗留：`findMissingPieces` 子搜索的预算仍按 CPU 秒，改成和主搜索一样有可复现的闸门（结果不随机器负载变）。

### 本轮改了什么（对应 5 条）

1. **药水爆手后保留未定的相对顺序**（原来每个入手集合只生成一种顺序，然后全场锁死）。
   - 场面顺序改用偏序表示：`RDBoardConstraints` 只存「左 < 右」的实体对，做传递闭包，只保留当前在场的随从。回合开始时的场面是全序；新下的随从没有约束。
   - 爆手（入手 k 张，场上 n 个，m = k mod n）时，进手的那批 C 必须是偏序的一个「下闭集」（不能有比 C 里某个随从更靠左、却不在 C 里的随从），大小为 m。枚举全部下闭集；结算后只加「C 中每个 < 不在 C 中的每个」这些对，其余相对顺序保持未定。
     - 舞动：结算后场面清空，约束自然清空，和原来等价。
     - 药水：场面保留，C 内部、C 外部的相对顺序仍然自由，后续再舞动时还能选。Codex 的复现局面（A、B、C 三个自由随从，药水复制两张）现在得到 {A,B} / {A,C} / {B,C} 三种入手集合。之后舞动只收一张时，{A,B} 内部未定，A 先、B 先都能走到。
   - 去重键 = 局面哈希 ^ 约束的位置掩码，约束不同的局面不会被合并。
   - 新测试 `testDeferredBoardOrderKeepsFreedomAfterPotion`：药水 → 舞动，0 费狐 / 母龙 / 鲨鱼，手牌上限 3。把逐格展开和延后决定两种 DFS 得到的终局集合逐个比对，再把延后决定的每条路径翻译成落位后用引擎原样重放。把旧的「全场锁定」写回去，这条测试会失败（已试过）。
   - `testDeferredBoardOrderReachesSameOutcomesAsFullPlacement` 改用同一个比对 helper（`assertDeferredMatchesFull`）。
2. **落位翻译时重映射实体 ID**。
   - `RDBoardOrder.assignPositions` 分两遍：
     - 第一遍按搜索语义重放，收集回合开始的场面链和每次爆手加的对；求一个拓扑序，平局按首次出现排。
     - 第二遍带落位重放：每次下随从插在场上所有拓扑序更靠前的随从后面。每一步新产生的实体按内容（除 `entityId` 之外的全部字段）和原线一一配对，维护旧 ID → 新 ID 的映射，后续动作里的 `entityId`、目标都换成新 ID。
   - 翻译或重放失败返回 nil。搜索丢掉这条线，计入 `placementTranslationFailures`；严格重放判失败。本轮 85 个通过案例的全部搜索结果里，这个计数都是 **0**（测试里断言）。
   - 新测试 `testPlacementTranslationRemapsEntityIds` 用 Codex 的复现局面：场上鲨鱼，手里狐、药水、舞动、7 张杂；线 = 下狐 → 药水 → 舞动收狐 → 下药水复制出来的狐。断言：只改 `position` 的翻译会抛错；`assignPositions` 给出的狐在第 0 格，复制品的 ID 被重映射，终局哈希和延后决定的线相同。
3. **清杂分支全部展开，结论分三类**。
   - `t2-wuhu-03` 和 `t2-daoqs-02` 截图上都有两处括号清杂（「两杂可清」）。现在各展开成 4 条线：不清（表里印的数字属于它）、只清第一张（晦之后，杂 ≤1 费）、只清第二张（刀 杂 舞）、两张都清。第三轮 `t2-wuhu-03#2`「两张都清」照抄了线 1 的二阶段数字，本轮去掉了抄来的数字。
   - 截图没印数字的分支只给出牌顺序，不带法力值，严格重放只核对「这个顺序能不能打出来」。结论新增「清杂分支可行（截图没印这一支的数字）」，算通过。
   - `token.maxCost`：「杂≤1费」只允许 ≤1 费的可清杂牌（实际只有弯刀合格）。
   - 公式不成立时，签名前加失败类别（`failureKind`），区分三种：
     - **印刷数字对不上**：去掉法力值、只按出牌顺序重放能过；
     - **爆手**：只有把手牌上限放到 30，按出牌顺序重放才能过；
     - **其他**：两种都过不了。
   - 结果：两行的「不清」支都是「爆手｜第15步「暗2」」；另外三支都可行。**两行整行成立**（测试打印「多分支行的整行结论」）。三支都要求把晦插在第 5 格，例如 `t2-wuhu-03#2`：`鱼5 刀1 暗-刀0 刀0 牛[舞龙]0 晦(第5格)4 弯刀3 刀2 舞2 鱼2 晦4 刀3 刀3 龙2 骨-晦2 暗-龙2 龙1 龙0`。
   - `t2-daoqs-02` 的「不清」支不改「刀1」（推演是刀0，但爆手和它无关）；三条清杂支带着「刀1 → 刀0」的 `tableErrata`。
4. **脱水的快枪费用改成固定值（待核）**。
   - 快枪生效（本回合进手）时，费用就是 `quickdrawCost`（1）。它不吃减费层（伺机待发 / 狐 / 刀油），也不吃费用附魔；减费层照样被这张牌消耗。第三轮的做法是先把基础费设成 1，再吃减费，能减到 0。
   - 依据：
     - 官方卡面「快枪：费用为 (1)」；
     - wiki 的费用规则：后设定的费用覆盖先前的，设定之后新产生的减费仍然生效。快枪这次设定发生在什么时刻，查不到；
     - 总指挥转述的玩家实测：快枪费用是固定值。
   - 没有官方确证，card-model H 节**标待核**。取这个口径的理由：它算出的费用不低于另一种算法，搜索不会报出打不出来的线。
   - 另查到**脱水是萨满牌**，本牌组和那版潜行者牌组都不能直接带，只能经持枪要挟这类发现拿到。
   - 单测补了两条断言：减费层 3 层时快枪费用仍是 1；不是本回合进手时按 3 费吃减费，结果 0。公式验证里没有一个案例用到脱水，这条订正不改任何结论。
5. **爆手排法数取 1 的损失，以及怎么补**（数据见「落位」一节）。
   - **什么时候会漏解**：每次爆手，主搜索只保留 3 种排法：现有顺序（默认），加上贪心分、构筑分各最高的一种，重复的去掉。如果斩杀要求的入手集合不是这几种之一（比如为了让第二次舞动收到特定的一张，第一次要先收一张分数不高的），主搜索就找不到。
   - **不限排法数的代价**：主搜索不限时，排法挤满了束，`t1-48p-06`、`t1-48p-07`、`t2-wuhui-03`、`t2-wuhui-04` 掉线（85 个通过案例里掉 4 个）。上限取 2～6、加上排法在束里的份额限制，各扫了一遍，每种设置都有案例掉线（见下表）。所以没有一个上限值能单独解决问题。
   - **本轮做法：三遍搜索，共用 40 万状态总预算**：
     1. 主搜索：排法上限 1，不变。
     2. 排法补搜 `boardOrderPass`：主搜索没斩杀时才跑。排法数不限，但非默认排法最多占束每层的 25%（`boardOrderVariantShare`），状态数最多用总预算的 25%。
     3. 采样补搜：仍没斩杀时用剩下的预算跑，排法上限 1。
   - 结果：**85 / 85 达标**。排法补搜救回了 5 个案例：`t2-wuhui-04`、`t2-wuhu-03#2 / #3`、`t2-daoqs-02#2 / #3`。`t2-wuhui-03` 仍靠采样补搜。
   - `RedDragonConfig.exact` 不设排法上限，也不跑补搜，单测里的穷举对比走它。

### 落位：怎么做的、状态数变了多少

- **规则**：舞动 / 幻觉药水按场上从左到右处理，手牌放不下的（最右侧的）烧掉。用户 09-11 已定。
- **偏序模型**（本轮）：
  - 下随从时可以插任意一格。所以亲手放下的随从，彼此之间、和已在场的随从之间的顺序都可以延后决定；只有回合开始时的场面顺序是定死的。
  - 状态带一个偏序（`RDBoardConstraints`），状态里 `board` 的顺序始终是它的一个线性扩展。
  - 爆手时枚举入手集合 C：C 是偏序的下闭集、大小 m = k mod n。结算后只加 C × (场上其余) 的对。舞动清空场面，约束随之清空；药水保留场面，C 内部、其余部分内部的顺序仍然自由。
  - 先按「进手的随从种类」去重（药水还要比位置掩码，因为场面保留），再结算，结算后按「哈希 ^ 位置掩码」去重。
  - 单测：舞动、药水 → 舞动两种局面下，延后决定和逐格展开的终局集合逐个相等；延后决定的每条路径翻译成落位后都能原样重放。
- **翻译回落位**：见「本轮改了什么」第 2 条。翻译失败的线丢弃并计数，本轮全部搜索结果计数为 0。
- **等价判定**：
  - 引擎 `legalActions`：没有按顺序处理全场的牌就只列最右；插进去后场面序列相同的只留一个。
  - 搜索 / 严格重放：下随从时不展开，爆手时按上面的方式展开。
- **逐格展开的代价**（沿 85 条严格重放路径）：共 1467 步，1150 步有可选落位；合法动作合计 26469，不含落位是 9967，**×2.66**。
- **爆手排法数（第 5 条）的扫参**。同测试配置，对 7 个敏感案例扫了以下组合，「掉线」= 搜索伤害低于目标：

  | 设置 | 掉线的案例 |
  |---|---|
  | 主 / 采样上限都是 1（偏序改完后的初始状态） | `t2-wuhui-04`（32 / 48）、两行清杂的 #2 / #3（34 / 48） |
  | 上限不限 | `t1-48p-06`、`t1-48p-07`、`t2-wuhui-03`、`t2-wuhui-04` |
  | 上限 1，只多保留构筑分最高的一种 | 同第一行，没变化 |
  | 上限不限 + 束内份额 0.1 / 0.25 / 0.4 | 清杂案例救回，`t1-48p-06`、`t1-48-10`、`t2-wuhui-03` 掉线 |
  | 上限 2 + 份额 0.25 | 清杂 #2 / #3、`t2-wuhui-03` |
  | 上限 3 + 份额 0.25 | `t2-daoqs-02#2`、`t2-wuhui-03` |
  | 上限 3 + 采样上限 1 | `t2-daoqs-02#2`（7 个案例合计 1,008,528 态） |
  | 上限 4 / 6 + 采样上限 1 | `t1-48p-06`；上限 6 时还有 `t1-48p-07`（上限 4 合计 1,091,273 态） |

  - 结论：放开排法数，对一部分案例来说解空间更完整，对另一部分来说束被排法挤占。单一上限做不到两头兼顾。三遍搜索的做法是：主搜索保持上限 1，所以原来能斩杀的案例状态数不变；只有没斩杀的案例才用 25% 的预算去试其他排法。
  - **仍然有损**：排法补搜只有 25% 的束位和 25% 的状态，采样补搜又回到上限 1。如果一条斩杀线既需要冷门排法，又要更宽的束，三遍都可能找不到。`RedDragonConfig.exact` 不设排法上限，可用来穷举复核。
- `RDEnemyMinion.damaged` 开局按未受伤算。T2b 接真实对局时，开局就带伤的敌方随从要置 true，否则背刺的目标判定会错。

### 搜索预算与补搜

- `maxStatesExpanded` 默认 40 万，是三遍搜索的总量。主搜索最多用 `(1 − samplingShare) × 总量` = 20 万；排法补搜最多拿 min(剩余, 总量 × 25%)；采样补搜拿剩下的。`cpuBudget` 3 s 只做兜底。`RedDragonConfig.exact` 不设上限。
- 85 个案例里主搜索最多 134687 态（`t1-48p-06`），没有一个撞上 20 万份额；总量最多 383333（`t2-wuhui-03`）。
- 主搜索没斩杀的案例：
  - 靠排法补搜斩杀（5 个）：`t2-wuhui-04` 76173 → 170417 态；`t2-wuhu-03#2 / #3` 56254 → 120445；`t2-daoqs-02#2 / #3` 73289 → 152675。
  - 靠采样补搜斩杀（1 个）：`t2-wuhui-03` 78040 → 383333 态。第三轮是 76337 → 278373，多出来的是排法补搜那一遍。
  - 7 个预启动不斩杀，按设计三遍都跑：`t1-pre-01`、`t1-pre-02`、`t1-pre-03` 两个、`t2-pre-01`、`t2-pre-02`。
- **待注意**：`t2-wuhui-03` 仍然只有采样束能找到（整手弹回成 0 费、最后连下两条龙），对参数敏感，扫参里多数设置都会让它掉线。

### 缺件闸门 / 彗星假设（之前所做，本轮未改）

- `findMissingPieces`：
  - 每个候选的份额 = `max(1, missingPieceMaxStates / 候选数)`，份额之和不超过总量（12 万）。

- 改法：
  - 引擎：手牌 / 边牌 / 牌库里有按场序处理全场的牌（`boardOrderMatters`）时，友方目标按实体全部列出。没有这类牌时场序不影响任何结果，按 `minionKey` 合并，它包含进哈希的全部字段。

- 回归测试 `testIdenticalFriendlyMinionsAtDifferentPositionsAreDistinctTargets`，用的就是复现局面：
  - 剩 3 费、对手 16 血；场面从左到右 1/1 阿莱 A、暗影施法者、鲨鱼、1/1 阿莱 B，都不能攻击；手里 −2 费骨刺、幻觉药水、8 杂。
