# Firestone overlay 调研

> 目的：为 Phase 1（SwiftUI 渲染）和 Phase 2（记牌器分区）提供一个**已验证的**参照物，
> 而不是凭印象。所有结论都标注了证据来源。

**许可证警告**：`Zero-to-Heroes/firestone` 仓库 **`License: None`**，即默认保留所有权利。
本文只记录**观察到的行为与设计**，可作为设计参考；**不得拷贝其代码或 SVG 资源**，
图标须自行绘制或另找可商用来源。

| 来源 | 说明 |
|---|---|

**120fps 是关键**：一帧 8.3ms，任何 100ms 以上的过渡都会留下 12 帧以上的中间态，测得出来。

测量方法：`ffmpeg -vf "crop=<卡表区域>,scale=1:1" -f rawvideo` 把每帧压成 3 字节的平均色，
一次解码得到整段的颜色时间序列，再找跳变。**比肉眼看拼图可靠** —— 本次调研中肉眼判断错了两次，
都是被这个方法纠正的。

## 一、动效：几乎没有

### 1.1 卡条插入：无动画，但有 ~125ms 的空白占位

抓到一次手牌从 8 张变 10 张（`318.70s`，逐帧间隔 25ms）：

```
帧14   正常
帧17   突然出现两行空白灰条，下方列表被顶下去    ← ≤25ms 内完成，位置即最终位置
帧20   空白条不动
帧23   空白条不动
帧26   空白条不动
帧29   空白条不动
帧32   内容瞬间出现：融合独角兽、镶铸水鬼
```

**没有横向滑入，没有位移，没有淡入。**新行瞬间出现在最终位置，
维持约 **125ms 的空白灰条**，然后内容瞬间填入。

这是**渲染延迟造成的占位符闪烁，不是设计出来的动效**。从 UX 角度这其实是缺陷。

### 1.2 关联卡牌高亮：硬切换，零过渡

鼠标悬停某张牌时，牌库/手牌中的关联卡牌（例：全部海盗）会高亮。测量卡表区域平均色：

```
+6.833s   delta=28   RGB (66,63,66) → (61,74,78)   高亮开启
   ...    中间 7.7 秒全是 ≤2 的噪声
+14.517s  delta=25   RGB (61,74,78) → (63,62,67)   高亮关闭
```

开启瞬间逐帧：**10 帧完全相同 → 1 帧跳变 → 14 帧完全相同，零个中间值。**
切换耗时 1 帧（8.3ms）。**没有淡入淡出。**

### 1.3 源码侧的交叉验证

| 检索 | 结果 |
|---|---|
| 1076 个 `.ts` 中使用 `@angular/animations` | **5 个**，全部不在记牌器（两个指令只用于新手引导，其余是窗口壳/成就/加载态） |
| 348 个 `.scss` 中的 `@keyframes` | **7 处**：tooltip 淡入淡出、加载转圈×3、通知抖动、`card-zoom`（死代码） |
| `deck-card` / `deck-zone` 模板 | 未使用任何动画指令 |
| 卡条自身的 transition | **被注释掉了**，注释原文 `Removing the transition fixes the flicker`，附 webkit 文字闪烁的 StackOverflow 链接 |

唯一生效的过渡是 `.scalable`（`decktracker-overlay.component.scss:29-56`）——
**整个面板**折叠/展开时的缩放 + 透明度，0.2~0.3s，`cubic-bezier(0, 0.26, 0.305, 1.65)` 带回弹，
`transform-origin` 玩家侧右上、对手侧左上。**不是卡条级别的。**

`BrowserAnimationsModule` 确实注册了（`legacy-feature-shell.module.ts:632`），
所以"不做动画"是**选择**，不是能力缺失。

## 二、布局

```
┌────────────┬──────────────────────────────┬────────────┐
│ 对手记牌器  │        炉石游戏画面            │ 玩家记牌器  │
│ （左边缘）  │   ┌──────────┐               │ （右边缘）  │
│            │   │ 计数器面板 │  ┌─────────┐  │            │
│            │   └──────────┘  │回合计时器│  │            │
└────────────┴──────────────────────────────┴────────────┘
```

三个独立窗口：两侧记牌器 + 计数器面板 + 回合计时器（后两者浮在画面上方区域）。

## 三、玩家记牌器的构成

自上而下：

1. **标题栏**：Firestone 图标 + 若干功能图标 + 最小化 + 关闭
2. **套牌行**：套牌名（超长截断为 `自定义 ...`）+ 复制图标 │ 手牌图标 + 数量 │ 牌库图标 + 数量
3. **分段**，每段一个居中标题 `<名称> (数量)` + 右侧折叠箭头：
   - `牌库中 (N)`
   - `手牌中 (N)`
   - `其他 (N)`
   - 对手侧额外有 `全局效果 (N)` 置顶

**分段标题自带数量**，这是我们 Phase 2.4 三行头之外的另一处信息呈现。

## 四、卡条结构

```
┌────┬──────────────┬─────────────────┬────┐
│费用│  卡牌名称     │  卡图（右侧渐隐）  │图标│
└────┴──────────────┴─────────────────┴────┘
```

- **费用格**按稀有度着色：紫=史诗、灰白=普通、蓝=稀有、橙金=传说
- **卡图**贴在右侧，向左渐隐融入底色（不是完整卡面，是局部裁切）
- **右端状态图标**：传说为星形徽记；源码中另有 `card_graveyard`（骷髅）、`card_burned`、
  `card_discarded`、`card_transformed`、`card_stolen`、`card_gift`、`dredged` 共 8 种
- **高亮态**：整行底色转青 **且** 费用格转青色

高亮只有三档（源码 `VisualDeckCard.highlight`）：`'dim' | 'normal' | 'in-hand'`。

尺寸实测见第七节。

## 五、计数器面板

独立窗口，有自己的标题栏 `计数器` 和折叠箭头。内部按 **`玩家` / `对手` 两列**排布，
每个计数器是「卡牌图标 + 数值」的绿色胶囊。

**这个设计值得借鉴**：我们现在的计数器（`CountersOverlay`）位置由 `SizeHelper` 算死、
不可拖动（见 PLAN Phase 5），而 Firestone 把它们收进**一个可折叠的独立面板**，
天然就可整体移动，也解决了"计数器数量变化时布局往哪长"的问题。

## 六、对我们的启示

**可以直接借鉴的**

- 状态用**图标**表达而非颜色/暗化，信息密度高且不抢视觉（对应 PLAN 2.7）
- 分段标题带数量
- 计数器收进单一可折叠面板，而非散落的独立窗口（对应 Phase 5）
- 卡图右侧渐隐的做法，既能认卡又不喧宾夺主

**我们应该做得更好的**

- **卡条插入的 125ms 空白占位是缺陷**，不该照抄。SwiftUI 下内容与布局同帧提交，不会有这个窗口。
- **跨分区移动可以做真正的动画**。Firestone 做不到是结构性的：每个分区独立 `*ngFor`、
  `trackBy: cardId`，卡牌换区就是在 A 销毁、B 新建，没有元素可供过渡。
  SwiftUI 的 `matchedGeometryEffect` 正是为此设计。
  **前提是 Phase 1.3「消灭每帧视图树重建」先落地** —— 每帧重建的视图树没有稳定身份，
  和 Firestone 卡在 DOM 重建上是同一类问题，区别在于我们能解决。
- **关联高亮值得加过渡**。Firestone 是 8.3ms 硬切换；我们的问题是高亮**太弱看不见**（PLAN 2.6），
  一个 100~150ms 的淡入既能强化存在感，又不会像位移动画那样干扰读牌。

## 七、尺寸实测 —— 这是我们要还原的目标

> 用户明确表示"视频里 Firestone 的尺寸是我自己玩着舒服的那种"，
> 而我们现在全屏下**卡条太宽、整体太高**。本节是那个目标尺寸的量化记录。

测量帧：`t=400s`，1920×1080 全屏，玩家侧显示 `牌库中(12) / 手牌中(9) / 其他(19)` 共 40 条卡条。
方法：`ffmpeg crop → scale=N:1`（列均值）/ `scale=1:N`（行均值）取一维序列，再找跳变；
分段标题与卡条之间有 1px 深色分隔线，用它数行距。

### 7.1 面板

| 项 | 实测 | 占屏比 |
|---|---|---|
| 玩家侧面板宽 | `x=1719..1889` → **171 px** | **8.91% W** |
| 对手侧面板宽 | `x=0..169` → **170 px** | 8.85% W |
| 玩家侧面板顶 / 底 | `y=28` / `y=957` | 高度随内容变，非满屏 |
| 玩家侧右边距 | 距屏幕右缘 **30 px** | 见下注 |

对手侧紧贴左边缘（`x=0`），玩家侧却离右缘 30px。**这 30px 大概率是用户自己拖出来的偏移，
不是设计常量**，还原时按 0 处理即可。

### 7.2 纵向单元 —— 所有元素都是"一行高"

| 元素 | 实测高度 | 占屏比 |
|---|---|---|
| 标题栏（Firestone 图标 + 功能图标 + 最小化 + 关闭） | 22 px | 2.04% H |
| 套牌行（名称 + 手牌数 + 牌库数） | 23 px | 2.13% H |
| 分段标题（`牌库中 (12)` + 折叠箭头） | 22 px | 2.04% H |
| **卡条** | **21 px** | **1.94% H** |

分隔线实测位置（玩家侧，`其他` 段 19 行）：
```
599 620 641 662 683 704 725 746 767 788 809 830 851 872 893 914 935 956
```
`(956-599)/17 = 21.0` —— **行距恒为 21px**，个别行 20px 是亚像素取整。
对手侧同一测法也是 21px（`177 198 219 240 261 282 303 324 345 366`），两侧一致。

**这是整套设计里最值得注意的一点：标题栏、套牌行、分段标题、卡条，四者高度几乎相同（21~23px）。**
整个面板是一个统一的行网格，没有任何一块比卡条明显高。
对比我们现在的顶部信息区（卡数 + 抽卡概率 + 疲劳 + 战绩，各自一行且行高不一），
差距不只在数值上。

### 7.3 卡条内部（171 px 宽）

```
x  1719      1741   1745                1790        1825        1889
   ├─ 费用格 ─┤ gap ├────── 卡牌名称 ──────┤ 卡图渐隐 ├── 卡图实体 ──┤
      22px     8px          ~45px            35px        65px
```

- **费用格 22×21 px** —— 几乎正方形
- 卡图从 `x≈1790` 开始渐隐浮现，`x≈1825` 之后是实体图，到右缘 `1889` 结束
- 名称区约占 47%，卡图可见区约占 38%

### 7.4 计数器面板

| 项 | 实测 |
|---|---|
| 整体 | `x=1509..1674` × `y=14..131` → **166 × 117 px** |
| 标题行「计数器」 | 21 px |
| 列头「玩家 / 对手」 | 17 px |
| 计数器胶囊 | 约 **79 × 30 px**，两列布局，行间距 ~5px |

### 7.5 和我们现在的对比

`HSTracker/UIs/Cards/CardSize.swift` 的五档预设：

| preset | 行高 pt | 面板宽 pt | 宽高比 |
|---|---|---|---|
| tiny | 17 | 108.5 | 6.38 |
| small | 23 | 146.8 | 6.38 |
| medium | 29 | 185.1 | 6.38 |
| **big（默认）** | **34** | **217** | **6.38** |
| huge | 52 | 331.9 | 6.38 |

**五档共用同一个宽高比 6.38 : 1**，因为宽度是从高度算出来的：
```swift
let kSmallFrameWidth = (kFrameWidth / kRowHeight * kSmallRowHeight)
```

**Firestone 是 171 / 21 = 8.14 : 1。**

| | Firestone | 我们 `.big` | 差 |
|---|---|---|---|
| 宽高比 | **8.14 : 1** | 6.38 : 1 | 我们的卡条**相对更粗短** |
| 占屏宽（@1920 逻辑宽） | 8.91% | 11.30% | 我们宽 **+27%** |
| 占屏高（@1080 逻辑高） | 1.94% | 3.15% | 我们高 **+62%** |
| 40 张牌总高 | 951 px（88% 屏高） | 1360 pt（**126% 屏高，溢出**） | — |

**结论：现有任何一档预设都表达不出 Firestone 的比例。**
按行高选 `small`（23）→ 宽度只有 147，比 171 窄 14%；
按宽度选 `medium`（185）→ 行高 29，比 21 高 38%。
**必须先把宽和高解耦**，这不是调参数能解决的，是缺一个能力。

### 7.6 为什么"全屏下"特别不 OK

`SizeHelper.trackerFrame()`（`:311-321`）：

```swift
let frame = NSRect(x: xOffset, y: offset,
                   width: max(trackerWidth, width),          // ← 绝对点值
                   height: max(100, hearthstoneWindow.frame.height - offset - yOffset))
return hearthstoneWindow.relativeFrame(frame, relative: false)   // ← keepRatio 默认 false
```

`relativeFrame` 只有在 `keepRatio: true` 时才缩放宽高（`:220-223`），
而记牌器用的是默认的 `false`。**所以面板宽度是绝对点值，完全不随炉石窗口缩放。**

而这些常量是按什么调的？`SizeHelper.swift:16-17`：

```swift
static let BaseWidth: CGFloat = 1440.0
static let BaseHeight: CGFloat = 922.0
// All size are taken from a resolution of BaseWidth*BaseHeight (my MBA resolution)
```

**原作者的 MacBook Air 分辨率。** 在 1440×922 下 217pt = 15.1% 宽、34pt = 3.69% 高 ——
那是它唯一"对"的地方。窗口一变大，占比就掉；变小，就涨。全屏且逻辑分辨率接近 1920×1080 时
正好落在"宽 +27% / 高 +62%"这个难看的位置。

缩放能力**是有的**（`scaleX` / `scaleY` + `keepRatio: true`），
但整个 `SizeHelper` 里只有 `experienceOverlayFrame()` 一处用了它。

另外：主题贴图全部是 **1x 的 217×34 PNG**，无 `@2x`
（`HSTracker/Resources/Themes/Bars/*/frame*.png`，`frame_mask.png` 是 218×35）。
所以改宽高比会直接拉伸这些贴图，Retina 屏上本来就已经是放大后的模糊结果。
这是尺寸重做绑定的第二个工作量。
