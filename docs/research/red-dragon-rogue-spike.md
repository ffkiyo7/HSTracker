# Spike：红龙贼 combo 提示器（2026-09-11 起）

> 与既有排期（Phase 1 T8 / Phase 2 / 4.3 / 5 / 收尾）**无关**的独立调研。目的是回答三个问题：
> ① 这个功能到底要什么效果；② 隔壁 Windows 的 `zcr0701/Red-Dragon-Calculator-Release` 是怎么做的、哪些能借鉴；
> ③ 在 HSTracker 里怎么落地、会不会跟排期打架。**本文只规划，不写代码。**

## 一、定位：学习 combo 的工具，不是自动斩杀器

用户原话（2026-09-11）的要点：

- 红龙贼打法多、出牌顺序多，手牌 / 场面每局不同，随机性拖慢学习速度，天梯纯靠自己练很吃力。
- 工具**只基于手牌**帮判断「这回合能不能斩杀」；**留牌 / 过牌由自己判断**，工具不管。
- 判断为可斩杀时，**不要直接把整套顺序摊开**。形式：overlay 在**手牌位置**给序号提示出牌顺序；
  同名多张要能区分（换色，或 `A1` / `B1` 这种字母 + 序号）。
- 明知「给序号 = 等于帮我算完了」，但要的是**一个验证自己思路的办法**，overlay 的顺序是兜底。
- 特殊情况：常规斩杀盖不住「血量 + 护甲」时，可能要**预启动、准备打多套 combo**——这是最难学的部分。
- 如果 win 项目有灰色做法（读内存 / 注入之类），我们不跟；只读日志，与 HDT 同级。

### 从原话推出的产品边界

| 要 | 不要 |
|---|---|
| 「能 / 不能斩杀」+ 最大伤害 vs 对方有效血量 | 留牌 / 过牌建议 |
| 序号提示（按需揭示，见三、2） | 一进回合就把整套顺序摊开 |
| 手牌位置上的轻量标记 | 大面板、文字长解释 |
| 只读 `Power.log` 派生的状态（HSTracker 已有） | 读内存、注入、模拟点击、任何自动操作 |
| 特定卡组自动启用，其余卡组不出现 | 通用斩杀计算器（那是另一个更大的功能） |

## 二、需求澄清：用户没说、但落地时绕不过的点

按「不决定就没法开工」的程度排序，**每条末尾是我的建议，用户可推翻**。

### 1. 揭示节奏 —— 「学习」二字靠这条撑

序号一出来学习就结束了。建议做成**三档，可在设置里选，默认第 1 档**：

| 档 | overlay 上看到什么 | 用途 |
|---|---|---|
| L0 判定 | 只一个角标：`可斩杀 28 / 27` 或 `最大 19 / 27` | 先自己想顺序 |
| L1 参与牌 | 参与 combo 的手牌被高亮（无序号） | 想不出来时给提示 |
| L2 顺序 | 手牌位置上的序号（`1 2 3 …`） | 兜底 |

从 L0 升到 L2 的触发：**热键**（一次按一档）。不做「N 秒后自动揭示」——盯着倒计时反而更不动脑。

**难度分层决定能不能升档（用户 2026-09-11 加）**：原表里的公式实战难度差很多。规则：

- 每条斩杀线有一个难度分。用户 2026-09-11 定：**重点看「逆序启动」**（先刀 / 先狐再鱼这类打破「鱼 → 狐 → 刀 → 暗 → 牛」定势的线），用「模板牌先后颠倒的对数」计，权重最重；其次缺件（缺零件的替代线本来就更难记）、中途插牌、操作数、边牌张数。不用「和模板前 n 张比编辑距离」那种生硬算法。T1 算，权重可调。
- 多条线可用时**按最简单的那条判定 / 处理**，不是伤害最高的。
- 最简单可用线是「基础」档 → **不允许升到 L2**，只给 L0 的能不能斩；只有难线可用 → 兜底引导默认开。阈值在 T2 里由用户按实战感觉调。

另一个更贴「验证思路」的形态是**答题模式**：不显示序号，但每打出一张牌，角标变绿（仍在某条斩杀线上）或变红（这张打出去已经不可能斩杀）。
这是「我先想，工具判卷」，比看序号更像学习。**建议 v1 就带**，因为它的实现和 L2 共用同一个搜索器——搜索器每次手牌变化都重算，「打错」等于「重算后无解」。

### 2. 多条斩杀线时显示哪一条

同一手牌常有多条可行序列，只显示一条是武断的。建议：

- L1 高亮时区分**「每条线都要用的牌」**（必打）和「有的线用、有的不用」（可选）—— 这对学习最有价值。
- L2 序号取**冗余最大**（打完伤害超出最多）的那条，超出的部分能吸收对手的意外护甲 / 治疗。

### 3. 同名多张、同名不同状态

overlay 是**按 entity**（手里每张牌各自的 `zonePosition`）画的，两张同名牌天然在两个位置，序号本身就能区分，`A1 / B1` 这种编码不一定需要。
真正要注意的是**同名但状态不同**：一张减过费一张没减。费用必须读 entity 的 `[.cost]`，不能读卡牌静态费用（见四、1）。

### 4. 随机与隐藏信息：抽牌是这套 combo 的一部分，躲不掉

**（被三、1 改写）** 原以为「只算确定性伤害、抽牌留 v2」就够，但红龙贼的 combo 链里**抽牌牌是正式零件**（行骗抽法术 + 随从、潜伏帷幕抽 2 随从、挖掘宝藏、垂钓时光探底），E.T.C. 还要从边牌里发现。不建模它们，大多数局面算不出解。

照 win 项目的哲学，**不算概率，全转成确定性分支**，v1 只做最省的两条：

- **折入主线**：牌库剩余随从数 ≤ 抽取张数时，抽到什么是确定的，直接算进主线。HSTracker 知道牌库剩什么（`Player.getDeckState()`），这一步**不需要用户勾选**——win 项目让用户手工维护牌库池，是它最重的交互负担。
- **标记分支**：剩余数 > 抽取张数时，主线**到抽牌为止**，角标标「后续取决于抽到什么」。分支树（每种抽牌结果各算一条）留 v2。
- 边牌发现（牛池）：HSTracker 的 `DeckSideboards` 已知三张，三选枚举即可，v1 就做。
- **缺件提示（用户 2026-09-11 加）**：异教地图 / 垂钓时光这类过牌，工具不展开、也不建议怎么过，但**要告诉用户此刻离斩杀还缺哪张牌**——对牌库剩余的每种 combo 零件各试一次「加进手牌再算」，能让伤害跨过对方有效血量的列出来（`缺：刀 或 晦`）。无解时才算，预算另计。

### 5. 对手侧的因素

必须进状态的：**嘲讽**（挡随从攻击）、**护甲**、**圣盾 / 免疫**、已知的奥秘数量（贼没法确切知道是什么，只能在角标旁标 `⚠ 对方有奥秘`）。
这些 HSTracker 都能读（见四、2），且 `BoardState` 已经在算「场面能不能打死英雄」。

### 6. 「预启动 / 多套 combo」怎么定义

**（被三、1 改写）**「只基于手牌」不够：预启动的本质是**上回合铺到场上的随从**（鲨鱼 / 晦鳞 / 刀油）这回合没有召唤失调，能参与场面交换腾格子，药水 / 舞动也是作用于场上随从。所以状态必须是 **手牌 + 我方场面（含「本回合刚下」标记）+ 敌方场面**，这三样 HSTracker 都现成（四、1~2）。

**什么时候该预启动（用户 2026-09-11 补）**：实战里用到幻觉药水 / 预启动的线，起因都是两种——①对方**护甲 + 血量超过了常规单回合公式的斩杀阈值**；②对方**场攻太高，我方必须下怪**（不铺场就死）。win 项目做「敌方场攻检测」正是为此。HSTracker 自带 `BoardState`（我方是否死于对方场面）和对方有效血量，所以 **v1 就能给「危险 → 该（预）启动」的提示**，成本很低：
- 对方有效血量 > 本回合最大伤害（T1 已算） → 角标标「单回合不够，考虑预启动」
- `BoardState.isPlayerDeadToBoard()` 或对方场攻接近我方血量 → 角标标「场面危险，必须下怪」
- 但最大的卡点仍是**手牌齐不齐**：缺件提示（二、4）要和这个信号并排显示，「危险但缺 X」和「危险且齐了」是两种不同的行动。
具体铺什么（预启动线本身）仍是 v2。

跨回合规划本身（「这回合铺什么、下回合打」）中间隔着对手一个回合，不可能精确。拆成两级：

- **v1：只回答「本回合最大伤害 vs 对方有效血量」**。差多少一目了然，「够不够、要不要先铺一轮」由用户判断——这正是用户说的「需要我自己判断」。
- **v2：「留哪几张下回合最大」**——假设不抽到新牌、对手不回血，算「本回合打一部分、下回合再打一部分」的两段方案。搜索空间翻倍，且假设太多，**等 v1 用顺了再说**。

### 7. 回合中途重算与重编号；序号不够表达的步骤

用户打出第 1 张后，剩下的牌要**重新编号**（而不是让 `2 3 4` 留在原位）。搜索器每次状态变化都跑一遍，输入要带上「本回合已打出的牌」（连击依赖它，`CardsPlayedThisTurnCounter` 已有）。

**（被三、1 改写）** 这套 combo 一回合最多 30 步、阿莱可打 20 次，手牌每一步都在变（弹回、复制进手）。「给手牌编 1~10 号」的形态只对**前几步**成立，之后靠重算重编号，实际效果是一个「**下一步**」指针。另外有三类步骤**不在手牌上**，序号表达不了：

- 场面交换：用哪个随从撞哪个（腾格子）
- 弹回 / 施法者的目标：暗影步收回**哪一个**（场上有两条龙时）
- E.T.C. 发现选哪张

建议：手牌序号只标**前 3 步**；第 4 步起不画；目标类步骤在**场上随从位置**画一个小标记（`SizeHelper` 有场面坐标）；再给一条一行的「下一步」文字（`暗影步 → 阿莱`）。这三样加起来才是完整的兜底。

### 8. 只在这副牌上出现

用**当前套牌是否含关键牌**判断启用，不靠用户手动开。其它卡组不出现任何东西。总开关放 `Settings`。

### 9. 正确性怎么验：离线回放，不靠打局

一个学习工具**算错比没有更糟**。验收不能只靠 🎮 打一局：

- 用过往对局的 `Power.log` 做**回放测试**：每到我方回合跑一次搜索器，人工核对若干回合的结论（有解 / 无解 / 最大伤害），固化成单元测试的 fixture。
- **路径重放校验（P0）**：搜索器给出的序列，输出前用同一套规则**从头重放一遍**，费用 / 格子 / 目标合法性全过才显示。win 项目的头号 issue 就是「算出的 64 伤线在游戏里打不出来」（三、4）。
- 顺带一个学习功能：回放时能报「上一局第 N 回合其实有斩杀」——这也是用户要的「学习过程」的一部分，成本很低，可放 v2。

### 10. 卡牌效果建模的维护成本

combo 相关的每张牌都要手写效果模型（费用、伤害、减费、抽牌、连击条件……）；非 combo 牌只需「费用 + 无伤害」。
版本更迭会换牌。**模型做成数据表（一个 Swift 文件里的结构体数组），不要散在代码里**，换牌只改表。

### 11. 性能与线程

**（被三、3 改写）** 原估「10 张手牌全排列 + 剪枝，200ms」太乐观：弹回 / 复制会让手牌循环再生，一回合深度可达 30 步。win 项目用 C++ 四路束搜索、总束宽 5300、3 秒预算，175 个场景仍有 7 个不是最优。

v1 的策略：**先做精确搜索（DFS + 状态哈希去重 + 三件套剪枝：费用不够即剪、达到理论上限即停、超过敌血即截断）**，在回放 fixture 上量耗时。够用就不做束搜索；不够再上单通道束搜索，正交多通道是 v3 的事。
硬要求：后台队列、可取消、每次状态变化去抖后重算；**预算按 CPU 时间**（`clock_gettime(CLOCK_THREAD_CPUTIME_ID)`）不按墙钟，否则同一局面在系统忙时给出不同答案；超时返回已找到的最好结果并**标注「被截断」**。不能在主线程跑。

### 12. 灰色地带的自我约束

只读日志、只显示信息、不自动操作——与 HDT / Firestone 的「场面伤害」计数器同级。win 项目若读内存，我们不跟（见三）。

### 1. 卡组：单一伤害源的 OTK，算的是「阿莱能打几次」

- **唯一伤害源**：生命的缚誓者阿莱克丝塔萨（`LEG_CS3_031`）战吼打脸 8。Release notes 里所有伤害值（48 / 64 / 80 / 112 / 160）都是 8 的倍数；搜索参数就是 `min_alex / max_alex`（1~10）。
- **三个引擎**：
  - 复制：幻觉药水 `SCH_352`（全场随从 → 1 费 1/1 进手，**战吼保留**）、暗影施法者 `OG_291`
  - 弹回：暗影步 `EX1_144`（-2）、舞动全场 `ETC_079`（全收回，**本回合费用设为 1**——win 项目按「各 -1」建模，是旧文本，以 `red-dragon-card-model.md` 为准）、赤烟腾武（另一版本）
  - 回费：晦鳞巢母 `CATA_111`（手中有龙回 2）、斯卡布斯·刀油 `BAR_552`（连击：下两张各 -2）、伺机待发、狐人老千、锯齿骨刺击杀减费
- **倍增器**：鲨鱼之灵 `TRL_092` 光环 = **随从的**战吼 + 连击双触发 → 阿莱一次 16、晦鳞回 4、刀油各 -4、暗影施法者一次进 2 张。**法术的连击（致聋术 / 垂钓时光 / 行骗）不翻倍**（官方文本「你的随从的战吼和连击」，见 card-model）。
- **「预启动」** = 上回合先铺鲨鱼 / 晦鳞 / 刀油，本回合它们没有召唤失调，能参与「场面交换」（平 A 清场腾格子），而且药水 / 舞动作用于**场上**随从，铺得越多收益越大。
- **「多套 combo」** = E.T.C. 边牌三选（「牛池」）+ 两条内置「完成线」（刀鱼腾牛晦 / 刀鱼狐暗牛晦）。
- 它建模了 24 张牌（cardId 齐，dbfId 没取到；`CATA_111 / DEEP_014 / JAM_022 / TLC_515` 英文名未核实），V1.4 又加了伊瑟拉、锋鳞、脱水快枪、持枪要挟 7 种发现结果。
- ⚠️ **这是 2025 年的牌表**。用户现在天梯用的版本可能已经换牌，**卡表必须以用户当前的牌组代码为准**（见六、4）。

### 2. 能力边界

| 项 | 它怎么做 | 对我们的含义 |
|---|---|---|
| 输入 | 只读 `Power.log`（hslog + python-hearthstone）。不读内存、不注入、不依赖 HDT。V1.4 起「对局结束自动上报整局回放」 | 与 HDT 同级，**比 HSTracker 自己还保守**（我们带 HearthMirror 读内存）。上报不做 |
| 输入字段 | 水晶 / 法力 / 本回合已出牌数 / 牌库是否已知 / 手牌（名 + **当前费用**）/ 我方场面（名 + 血 + 费 + **是否本回合刚下**）/ 敌方场面 / 奥秘 / 武器 / 减费状态 | 抄这个 schema，`name` 换成 cardId。**没有敌方英雄血量 / 护甲**，斩杀靠 `lethal_threshold` 剪枝 |
| 输出 | 本回合**最高伤害的完整出牌序列**（分轮显示，缩写 + 颜色方块）+ 一棵「遇发现 / 抽牌就分叉」的 WhatIF 分支树。**没有留牌 / 过牌建议**；「预启动建议」V1.2 有、V1.3 删了 | 和用户要的方向一致：只算本回合 |
| 交互 | 局面自动跟日志，**计算要手动点按钮**。用户还要手工维护「牛池」「牌库剩余随从」勾选 | 牌库剩余我们能自动算（`getDeckState()`），边牌我们也知道（`DeckSideboards`） |
| overlay | **没有。** 独立小窗 + 分支树窗 + 主窗，不画在游戏上，不定位手牌 | 手牌位置序号是我们自己的新东西，没有先例可抄 |
| 灰色地带 | 无读内存 / 注入 / 改文件 / 自动操作的证据 | 我们只用 `Logging/` 链路，风险严格低于 HSTracker 基线 |

### 3. 计算机制：多通道正交束搜索

- 不是穷举也不是普通 DFS：**四路并行束搜索**，总束宽 5300，默认 3 秒预算，宣称覆盖 95%+；全库 175 个场景**最新版仍只有 168 个最优**。
- **最值钱的结论**：V1.4 把 4 条「重复堆宽」的通道换成 4 条**正交**通道（共识 2000 / 操作空间 1200 / 回收放大 1200 / 突破潜力 900），覆盖不变、快 1.9~2.1 倍、伤害上限 112 → 160。作者论证了「与主通道相关的启发切出来只会让并集坍缩」。**多路搜索的收益来自正交，不来自多。**
- 剪枝：全局 Top-K **+ 按龙数分桶保底**（否则「低龙数但在深蓄力」的桶被整个砍掉，V1.1 因此漏解）；`only_best_damage`（达到理论上限即停）；`lethal_threshold`（超过敌血截断，提速 50~100%）；状态哈希去重。
- **随机效果全部转成确定性分支，绝不算概率期望**：发现类枚举全部结果；抽随从从「牌库剩余」池展开；**缺失数 ≤ 抽取数时折入主线不分支**；池空禁止虚构抽牌；剩余不足时分支降级；牌库未知时异教地图直接放弃。
- **信任日志的当前费用**：从日志注入局面时直接用 `GameTag.COST`，不重算减费栈——炉石已经算好了。只有向前推演时才自己维护减费栈（刀油「一层 2 槽」：随从消耗槽、法术不消耗）。
- 时间预算 V1.4 从墙钟改成 **CPU 时间**：系统繁忙时同一局面「64/4 被截成 32/2」。

### 5. 可复用性小结

- **思路直搬 Swift**：状态字段清单、卡牌效果数据化（`CardDef` 不可变 + `enum Effect` 带关联值，状态值语义深拷贝、卡表静态共享——Swift struct 天然就是这个模型）、正交束搜索、龙数分桶、随机 → 分支、三件套剪枝、CPU 预算、目标作用域枚举（法术无合法目标禁打、随从战吼缺目标仍可裸下）、场面交换逐对结算不撞尸。
- **不用做**：日志解析、实体树、牌库跟踪、卡库、窗口体系——HSTracker 全有。
- **HSTracker 内的架构范本**：`BobsBuddy/BobsBuddyInvoker.swift:26-35`（迭代上限 + 分级时间预算）、`LethalResult` / `ExitConditions` / `BobsBuddyState`。**但求解器直接写 Swift，别再引 Mono。**
- **要主动做得比它好的两处**：牌库剩余自动算；边牌自动读。

## 七、overlay 落点：SwiftUI `RootOverlayView` 画布（已决）

**为什么不是 AppKit 点位表**（`CardHudContainer` 那套）：

- 我们要画的不止手牌序号，还有**场上随从标记 + 一行「下一步」文字 + 角标**，AppKit 路线要开 3 个 `OverWindowController`，每拍各自按 `SizeHelper` 重设 frame；`RootOverlayView` 是**一张全屏透明画布**，一次放下全部。
- `RootOverlayWindow` 已经处理了跟窗、全屏切 Space 时的 hide + reshow（`Game.swift:714-747`）、默认点击穿透（`RootOverlayWindow.swift:40`）；构筑模式下它本来就开着（`ConstructedMulliganGuideV2View` 挂在里面），**不用改显示条件**。
- 整个项目（Phase 1、上游）都在往 SwiftUI 走；上游 3.6.8 修的 macOS 26 崩溃就是 AppKit `lockFocus` 手绘惹的。
- 序号重编号、答题模式的绿 / 红变化，SwiftUI 动效免费。

**落点**：

- 挂点就是 `RootOverlayView.swift:172` 那句注释「Future SwiftUI overlay features attach here」，放在**内层 1080 画布**里（`:72-146` 那个 `ZStack`，随窗口等比缩放）而不是外层固定像素层。
- `RootOverlayViewModel` 加一个子 view model 属性。**上游文件只碰这两行**，其余全在新文件，控制合并冲突面。
- 坐标换算：`Game.swift:4957-4972` 的手牌公式给的是**窗口宽高的比例**（`offsetX` 过 `getScaledXPos` 后仍是横向比例，卡高 `0.5 × 窗高`），画布是等比缩放的，所以 **canvas 坐标 = 比例 × `canvasWidth`（横）/ × 1080（纵）**，不需要另外的像素换算。场面随从的横向位置 `SizeHelper` 里有同类公式。
- 标记本身非交互，**不报 `InteractiveRegionPreferenceKey` / `HoverRegionPreferenceKey`**，窗口保持穿透。
- 悬停手牌时游戏会放大那张牌，序号要跟着让开：先做成「悬停时整组隐藏」（`Game.swift:4953` 已知 hoveredCard），够用再细化。

### 记法

三个表头概念，**视频作者的原定义**（`red-dragon-formulas-concepts.png`）：

| 列 | 定义 | 对搜索器的含义 |
|---|---|---|
| **水晶数** | 启动公式时的法力水晶数量。刀油削弱后引入回费随从（以前的鲍勃、现在的晦鳞巢母），水晶不足会让回费亏掉，所以单列。极限水晶启动是素材局，实战少见 | = `Player.maxMana`（**不是**当前法力）。回费上限受它约束：晦鳞回 2 / 4 不能超过水晶上限 |
| **费用数** | 经过各种偷费后、启动前的**实际可用费用**。偷费 = 硬币、伺机 + 骨刺、提前步老千、步鱼屯费等 | = 启动那一刻的 `Player.currentMana` + 手里还没打的币 / 伺机等零费偷费。搜索器不需要这个数，它是从手牌自然推出来的；但 fixture 里要按它反推起始手牌 |
| **杂牌数** | 不分真假杂：随从牌、偷费牌（硬币、伺机、骨刺）**之外**的牌统称杂牌。涉及特殊杂牌或可清杂牌时表中标注 | 关系到**手牌上限 10**：药水 / 暗影施法者往手里塞复制，满手会烧掉。杂牌越多，能进手的复制越少 |
